- Baseline: `origin/main` commit `19686fb8a61b95a855013508b30a73ddde20377c`

## 원인

운동은 numeric Room ID와 stableKey를 함께 사용했고, program/workout/analysis/backup
경로마다 identity 해석이 달랐습니다. 239개 seed에는 중복 운동, generic split,
legacy CSV placeholder와 일관되지 않은 unilateral 명칭이 남아 있었습니다. 백업은
첫 오류에서 중단해 전체 무결성 문제를 한 번에 설명하지 못했습니다.

## 변경 내용

### stableKey-only identity

- `Exercise.stableKey`를 primary key이자 유일한 application-level 운동 identity로
  고정했습니다.
- `WorkoutEntry`와 `TrainingProgramItem`은 nonblank `exerciseStableKey`만 저장합니다.
- 사용자 운동은 이름에서 유도하지 않은 UUID stableKey를 유지하며 rename은 key를
  바꾸지 않습니다.
- Room `24 -> 25` migration은 numeric reference를 stableKey로 backfill하고 final
  table의 exercise ID column을 제거합니다.
- ID 0, dangling row, blank key, deleted placeholder와 ambiguous split은 조용히
  삭제하거나 추측하지 않고 migration issue로 남깁니다.

### backup and restore

- Restore CSV format을 `8`로 올리고 numeric exercise ID 없이 canonical stableKey만
  기록합니다.
- manifest의 app/format/timestamp/entity count/content hash를 검증합니다.
- destination stream을 열기 전에 모든 blocking error와 warning을 수집합니다.
- blocking error가 있으면 destination을 쓰지 않습니다.
- new-format restore는 count/hash/key를 검증해 restore plan을 만든 뒤 한 Room
  transaction에서 적용하고 post-restore validation 실패 시 전부 rollback합니다.
- Workbook legacy map은 old-format importer에서만 exact match로 사용합니다.
  정상 runtime은 name/fuzzy/contains fallback을 사용하지 않습니다.
- 작업 상세 report는 성공/경고/실패 stage와 진단을 저장하며 최근 20개만 보존하고
  backup payload에서는 제외합니다.
