# v0.5.0.29 release notes

## Summary

v0.5.0.29 corrects the app-visible time-series execution path. Heavy
compatibility analysis no longer runs synchronously from a Compose `onClick`.
The screen now performs typed preflight, executes through a ViewModel-owned
coordinator and background service, reports truthful stages, and separates
statistical unavailability from unexpected software failure.

The visible feature is now named `탐색적 시차 분석` (Exploratory lag analysis).
It is not presented as causal proof or as the completed strict Bayesian
PHASE B-E pipeline.

## Root causes

- `LaggedTimeSeriesAnalysisContent` constructed and ran
  `LegacyTimeSeriesAnalyzer` directly from Compose, so CPU-heavy work occupied
  the UI thread.
- The screen had no active-job owner, background dispatcher, cancellation,
  duplicate suppression, or stale-request protection.
- No preflight exposed transformed common weeks or estimator rows before the
  user pressed Analyze.
- Expected statistical inability and unexpected runtime exceptions did not
  have distinct product states.
- Compatibility output was labeled like a completed Bayesian analysis even
  though strict PHASE B-E remain future contracts.

## Execution path

Before:

```text
AnalysisScreen -> AnalysisLabUi -> Compose onClick
  -> LegacyTimeSeriesAnalyzer -> alignment/selection/fit/shock/result -> UI
```

After:

```text
AnalysisScreen -> TrainingViewModel -> TimeSeriesAnalysisCoordinator
  -> TimeSeriesAnalysisService on Dispatchers.Default
  -> LegacyTimeSeriesAnalyzer -> typed state -> AnalysisLabUi
```

## Preflight and state

- States: `Idle`, `PreflightReady`, `Running`, `Success`, `Unavailable`, and
  `Failed`.
- Preflight checks required X/Y/Z metrics, horizon, calendar range, aligned
  weeks, transformed common usable weeks, internal gaps, variation, requested
  estimator rows, and the compatibility route's model-size-dependent minimum.
- Missing weeks remain missing. They are not forward-filled or converted to
  zero.
- Analyze is disabled only when preflight proves the request cannot be
  attempted. Later estimator failure remains a typed `Unavailable` outcome.
- Running reports named stages without fabricated percentages.
- Software failures show a safe message, retry action, and diagnostic ID;
  normal unavailable results show a typed reason and relevant next step.

## Concurrency and performance

- One coordinator owns the active structured-concurrency job.
- Duplicate execution requests are ignored while the same request is running.
- Parameter changes cancel/invalidate old work; monotonically increasing
  request tokens prevent stale completion from overwriting newer state.
- Screen disposal cancels the owned job and `CancellationException` is never
  converted to failure.
- Per-request performance diagnostics record stage durations and the
  conceptual candidate × response × rolling-origin × lag × horizon model-fit
  bound. There is no brittle production millisecond threshold or global cache.

## Scientific boundary

- Strict PHASE A remains preparation-only and is not consumed by the visible
  compatibility route.
- Strict PHASE B BVAR posterior, PHASE C Bayesian Local Projection, PHASE D
  Johansen/Bayesian VECM, and PHASE E final ranking/comparison remain future
  contracts.
- The strict 32-week contiguous diagnostic, lifecycle states, fail-closed
  required-series handling, transformations, row plans, scaling, response
  scale, and shock boundaries were not weakened.
- There is no silent strict-to-compatibility fallback.
- Existing compatibility estimator formulas and successful numeric fixtures
  are unchanged.

## User-visible changes

- The screen displays selected X/Y/Z, requested horizon, usable-history
  preflight, blockers, and warnings before execution.
- A spinner and exact execution stage appear immediately while running.
- Success shows the actual compatibility model, requested and used horizon,
  common and actual estimation observations, response, uncertainty, and
  warnings.
- Detailed diagnostics remain expandable; raw stack traces are not displayed.
- All new states have Korean and English presentation coverage. Localization
  audit reports zero unexplained production or English-mode leaks.

## Files and ownership

- `TimeSeriesAnalysisExecutionModels.kt`: typed request preflight, stage,
  performance, state, and failure contracts.
- `TimeSeriesAnalysisService.kt`: preflight and background execution boundary.
- `TimeSeriesAnalysisCoordinator.kt`: active job, request token, cancellation,
  duplicate, retry, and stale-result ownership.
- `TrainingViewModel.kt`: screen-facing actions and `StateFlow`.
- `AnalysisScreen.kt` / `AnalysisLabUi.kt`: state collection and rendering only.
- `BayesianTimeSeriesAnalyzer.kt`: existing compatibility calculation plus
  stage reporting and typed unavailable classification.
- `tools/check_time_series_numeric_sources.py`: Compose/strict boundary guard.
- localization authority assets: Korean/English state presentation; generated
  exact-map chunks avoid the JVM single-initializer size limit.

## Remaining limitations

- The visible result is still the existing exploratory compatibility analysis,
  not a strict Bayesian posterior.
- Preflight can prove a request impossible, but readiness cannot guarantee that
  every later numerical fit or shock identification will succeed.
- Strict PHASE B-E require separate scientifically governed implementation.
