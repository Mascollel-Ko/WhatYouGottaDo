# v0.5.0.24 release notes

## Purpose

v0.5.0.24 makes exercise backup and restore self-contained without changing
exercise identity. It follows the v0.5.0.23 Korean metadata display authority
commit and preserves that work unchanged.

## Cause

Earlier backups depended too strongly on the destination catalog. Editable
exercise metadata could fall back to seed values, catalog-removed identities
could be rejected, and entry idempotence could collapse records that looked
identical even when they were distinct source events.

## Contract

- `stableKey` is the exercise identity.
- Current built-ins use the current canonical display name.
- Represented editable exercise/runtime metadata from the backup wins.
- Current canonical system fields remain current.
- Derived analysis fields are rebuilt.
- Custom exercises preserve exact stableKeys and represented metadata.
- Catalog-missing identities restore inactive and history-only.
- Relation snapshots replace complete represented relation domains.
- Explicit empty differs from a missing old-format field.

The typed registry contains 109 fields: 2 `IDENTITY_STABLE`, 4
`CURRENT_CANONICAL_NAME`, 95 `BACKUP_SNAPSHOT_WINS`, 4
`CURRENT_CANONICAL_SYSTEM_VALUE`, and 4 `DERIVED_REBUILD`.

## Format and persistence

- App version: 0.5.0.24 / 500024
- Backup format: 10 -> 11
- Restore schema: 9 -> 10
- Room schema: 27 -> 28
- New backup row: `exercise_metadata_snapshot`
- New nullable unique field: `WorkoutEntry.backupSourceId`

The snapshot row stores stableKey, field key, field scope, value encoding,
serialized value, and explicit-empty state. Old supported backup formats remain
readable. A one-transaction restore follows complete preflight validation.

## Behavior

Current catalog additions are preserved. Missing historical exercise rows are
materialized only when referenced. Program and workout graphs remain readable.
Distinct source IDs preserve legitimate identical-looking entries, while a
repeated restore of the same source remains idempotent. Runtime overrides and
restored role relations survive seed refresh and database reopen.

No current-catalog blanket allowlist or runtime display-name fallback was added.

## Rollback

Revert the application commit and migrate forward from Room 28 in a subsequent
release if needed. Do not downgrade a user database destructively. Existing
backup formats remain accepted by the compatibility parser.
